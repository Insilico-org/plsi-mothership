# Longevity Mothership v0.2.0 -> v0.3.0

Moving the Mother bot and each steward's machine to v0.3.0 without losing a stored contribution, a pending note
or a token. The Mother reads this file once, when it finds its checkout on v0.3.0 with a store written by v0.2.0;
a steward follows the **Steward machines** section by hand.

## Order

The Mother, the relay and PLSI change together, in this order:

1. The Mother's repo: `v0.3.0-dev` merged into `main` (the Mother bot pulls `main`).
2. The relay redeployed (the steward's deploy guide).
3. The Mother bot and every steward machine updated (below).
4. Only then PLSI v0.3.0 goes out: its research notes carry `tags`, `hallmarks` and `plsi_version`, which a v0.2.0
   Mother refuses as unknown fields.

## What is new

- **Research note tags.** Each item may carry `tags` (1-5 MeSH descriptors `{mesh, label, tree}`) and
  `hallmarks` (the twelve hallmarks of aging) in place of the four-value `topic`. The gate checks their form; a
  tree number's letter is its MeSH branch.
- **The PLSI version** (`plsi_version`) on every file PLSI 0.3.0 sends. It is optional, so a note from an older
  PLSI is still taken in and shown as "before 0.3.0". It appears in `research intake`, `research list`, the
  review card, the research digest, `feedback list` and the feedback digest (`versions`).
- **Long notes.** A note too long to attach sends its report as the data file `report.md` in its zip; the note
  itself is always its own `.json` attachment. A note inside the zip (`note.json`) is still read.
- **Research store layout.** Notes are filed by status, sender and project:
  `research/<pending|accepted|rejected>/<sender id>/[<project title> · <id>/]<receipt>/`, with
  `research/senders.json` mapping each address to its pseudonymous sender id. Notes stored in the v0.2.0 flat
  layout (`research/<receipt>/`) are still found by every command; `mother research tidy` moves the decided ones.
- **Research projects.** A note may name its project (`{id, title}`); `research list --project <id>` filters by it.
- **Statistics in notes.** A mean with its SD, a CI and a p-value are no longer taken for identification numbers;
  a dotted date before a full stop is still a date.
- **The stewards' dashboard.** A Google Sheet, "Mothership dashboard", at the top of the shared drive (tabs
  Overview, Research notes, Last 7 days; never an address), rebuilt by every command that changes the store and on
  demand by `mother dashboard`. It needs the Google Sheets API (below).
- **Deletion retires the install** (relay). After a `delete_all`, the install that asked is revoked once it reads
  its deletion confirmation; a later join needs a new code.

## The Mother bot

1. **Code.** In the Mother's checkout: `git -C <repo> pull` on `main`, then
   `python -m pip install -e "<repo>[drive]"`. `pip show plsi-mother` says version 0.3.0.
2. **Google Sheets API.** In the Google Cloud project of the service account in `MOTHER_DRIVE_CREDENTIALS`, turn on
   the Google Sheets API (the Drive API is already on). Without it every store change still works and reports a
   `dashboard` refusal.
3. **First dashboard.** `mother dashboard`: it creates the Sheet at the top of the shared drive. Tell the stewards
   where it is.
4. **Tidy the old layout.** `mother research tidy`: decided notes from v0.2.0 move to `accepted/` or `rejected/`;
   pending ones stay where they are until decided. Run it once; running it again moves nothing.
5. **Rules and routines.** Re-read `mother.md` and the skills `research` and `feedback`, which changed:
   - the review card shows each note's tags and hallmarks and its PLSI version;
   - a long note's report is its data file `report.md`, read in full like an embedded report;
   - the weekly feedback digest gives reports by role and by PLSI version, and names the version beside each
     frustration: one from an older version than the current release may already be fixed.
   Update the routines of `mother.md` §7 to these instructions (a routine keeps the text it was saved with). No
   routine is added or removed.
6. **Secrets.** None new and none changed: `MOTHER_STORE`, `MOTHER_DRIVE_CREDENTIALS`, `MOTHER_STEWARDS`,
   `MOTHER_ACTOR`, `MOTHER_RELAY_URL` and `MOTHER_RELAY_INTAKE_KEY` stay as they are. `MOTHER_RELAY_ADMIN_KEY` is
   still never in the Mother's secret store.
7. **Check.** `mother research list` lists every stored note with `plsi_version`; `mother feedback digest --since
   <seven days ago>` has `versions`; the Sheet shows the stored notes. Then tell the stewards in one message:
   "The Mothership is on v0.3.0: notes show their MeSH tags and PLSI version, and the dashboard Sheet is at the top
   of the shared drive."

## Steward machines

Each steward's own machine (never the Mother's account) runs the commands that need the admin key and store writes
(`mother publish`, `mother professional invite|invites|revoke`).

1. `git -C <checkout> pull`, then `python -m pip install -e "<checkout>[drive]"`.
2. Turn on the **Google Sheets API** in the Google Cloud project of your own service account
   (`MOTHER_DRIVE_CREDENTIALS` on your machine): store changes made from your machine rebuild the dashboard too.
3. No new environment variable. `MOTHER_RELAY_URL`, `MOTHER_RELAY_ADMIN_KEY`, `MOTHER_STORE` and
   `MOTHER_DRIVE_CREDENTIALS` stay as they are.
4. Read `steward.md` again: "See where things stand" is now the Sheet, or `mother dashboard`.
5. Never run a store write from your machine while the Mother's wake is running (unchanged).

## Rollback

All three sides go back together: the relay to its previous deployment, the Mother's `main` to the
commit before the merge and `pip install -e` again, and PLSI held at v0.2.1. v0.2.0 looks for a note only at
`research/<pending|accepted|rejected>/<receipt>/` and `research/<receipt>/`: a note taken in by v0.3.0 sits one or
two folders deeper (sender, project) and is invisible to a rolled-back Mother until its `<receipt>/` folder is moved
up by hand. Contributions, deletions, receipts and tokens need nothing.
